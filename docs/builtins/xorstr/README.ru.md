# Шифрование строк на этапе компиляции (`xorstr`)

## Обзор

NeverC предоставляет двухуровневое шифрование строк на этапе компиляции для кода на C, предназначенное для сценариев безопасности, где открытые строки (имена API, пути реестра) не должны быть видны в скомпилированном бинарном файле.

- **Уровень 1 — Явный макрос**: `NC_XORSTR("string")` / `NEVERC_XORSTR("string")` для точного управления каждой строкой
- **Уровень 2 — Автоматический IR-проход**: `-fencrypt-call-strings` для автоматического шифрования всех строковых аргументов в вызовах функций

Оба уровня используют буферы на стеке (без выделения в куче), отдельные потоки ключей для каждого экземпляра и volatile-очистку. На границе генерации машинного кода явные вызовы декодера `NC_XORSTR` перешифровываются и разворачиваются непосредственно в каждой точке вызова; в итоговом объекте не остаётся общей функции-декодера.

---

## Быстрый старт

```c
#include <neverc/xorstr/xorstr.h>
FARPROC addr = GetProcAddress(hModule, NC_XORSTR("NtQuerySystemInformation"));
```

```bash
neverc -fencrypt-call-strings main.c -o main
```

---

## Этапы защиты

1. **Sema** шифрует каждый литерал отдельным ключом. При seed `0` компилятор получает свежую энтропию ОС; `-fstring-encrypt-key=` задаёт детерминированный 64-битный результат.
2. **Промежуточный IR / вход LTO** сохраняет непрозрачный, неспециализируемый вызов декодера, чтобы оптимизации не восстановили открытый текст в IR.
3. **Финальная граница машинного кода** расшифровывает и заново шифрует ciphertext на стороне компилятора, выбирает форму цикла для каждой точки вызова, разворачивает её на месте и удаляет декодер, граф помощников, ABI-якорь, состояние маршрутизации и семантические имена.
4. **Очистка** устанавливается до оптимизации или передачи provider и повторяется в финальном хвосте; повторный проход идемпотентен и исправляет размещение после изменений CFG.

### Разнообразие декодеров

Последовательность состояний, константы, ciphertext и эквивалентные выражения над байтами зависят от seed и точки вызова. Один из возможных вариантов — `a + b − 2 × (a & b)`. Volatile-загрузки состояния/ciphertext мешают свёртке констант, а `nooutline` не позволяет Machine Outliner заново создать общий декодер после финализации IR.

Таким образом, у IDA нет стабильной отдельной функции, которую можно распознать или эмулировать один раз. Это не означает, что открытый текст, необходимый работающей программе, невозможно наблюдать динамической инструментацией.

## Автоматическое шифрование и очистка

`-fencrypt-call-strings` выполняется до IPO, после обычной оптимизации и ещё раз после каждой поздней обычной или подключаемой IR-фазы. LTO применяет такое же обязательное запечатывание после provider- и pre-codegen-хуков.

Обрабатываются прямые и косвенные аргументы `CallBase`, происходящие из приватных принадлежащих компилятору литералов `unnamed_addr`; сохраняется семантика GEP, cast, `freeze`, `select`, PHI и продвигаемых локальных слотов указателей. Пропускаются intrinsic, inline asm, внешне видимые или пользовательские массивы и слишком большие литералы. Передача защищённого литерала через `musttail` безопасно завершает компиляцию ошибкой.

`XorStrCleanupPass` полностью обнуляет буфер volatile-операцией `memset` перед каждым достижимым `ret`, `resume`, выходящим к вызывающему `cleanupret` и неперехваченным unwind `catchswitch`. Небезопасное или неполностью отслеживаемое хранилище отклоняется, а не очищается частично.

## Справочник флагов компилятора

| Флаг | Описание |
|------|----------|
| `-fencrypt-call-strings` | Включить автоматическое шифрование строк |
| `-fno-encrypt-call-strings` | Отключить автоматическое шифрование |
| `-fencrypt-call-strings-max-len=N` | Максимальная длина в байтах (по умолчанию: 1024) |
| `-fstring-encrypt-key=0xHEX` | Задать полный 64-битный seed; `0` использует свежую энтропию |

## Границы вывода и воспроизводимость

- `-fno-lto` выполняет финализацию при нативной генерации кода frontend.
- Auto-LTO и Full LTO сохраняют непрозрачный декодер в pre-link bitcode, а затем перешифровывают и разворачивают его после межмодульной и plugin-оптимизации.
- После pipeline, заменённого provider, и поздних plugin-проходов всегда выполняются обязательные шифрование, очистка и финализация.
- При seed по умолчанию независимые нативные сборки различаются; whole-link- и partition-кэши, способные воспроизвести старый защищённый код, обходятся.
- Ненулевой seed намеренно детерминирован и пригоден для кэширования: одинаковый вход и одинаковый полный 64-битный seed дают одинаковый защищённый код.
- `-emit-llvm` и pre-link bitcode являются промежуточными артефактами и намеренно сохраняют непрозрачный ABI. Гарантия отсутствия общего декодера относится к успешно сгенерированному финальному машинному коду.
